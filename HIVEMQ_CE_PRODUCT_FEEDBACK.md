# HiveMQ CE — Product Feedback from a First-Time Self-Managed Deployment

**Context:** Deployed HiveMQ CE 2025.5 on a Ubuntu 24.04 VPS (Docker) to validate an MQTT-based IoT architecture for a MAP (Modified Atmosphere) HoReCa device. ESP32-S3 device publishing telemetry over MQTT/TLS. Built with Claude Code as the development assistant. Total time to working end-to-end: ~90 minutes.

This feedback is written from a product director perspective — what broke the experience, what worked well, and what I'd prioritize to improve the CE developer journey.

---

## Friction Points (roughly in order of impact)

### 1. Control Center removed from CE — not documented prominently
**What happened:** `config.xml` includes a `<control-center>` section. The broker starts, port 8080 is mapped by Docker, but nothing serves HTTP. There's no warning in the logs that Control Center is an Enterprise-only feature. The config section is silently accepted and ignored.

**Impact:** A developer following any documentation from HiveMQ 4.x expects a management UI. They'll debug port accessibility, firewall rules, and Docker networking before discovering the feature was removed. I wasted ~20 minutes here.

**Recommendation:**
- Log a clear `WARN` on startup when `<control-center>` is present in CE: *"Control Center is not available in HiveMQ Community Edition. Remove this section or upgrade to HiveMQ Platform."*
- Update the CE quick-start documentation with a visible callout: *"CE does not include the Control Center UI."*
- Consider open-sourcing a minimal read-only broker dashboard for CE, or officially endorsing one (MQTT Explorer, HiveMQ's own web client). The absence of any observability UI is the biggest gap between CE and a real developer-friendly broker.

---

### 2. TLS setup requires silent debugging of file permissions
**What happened:** HiveMQ CE runs as a non-root user inside the container. Certificate files generated by root (chmod 600 by default from `openssl`) can't be read by the HiveMQ process. The error message is: *"Not able to create SSL server context. Reason: Cannot find KeyStore at path '/opt/hivemq/certs/hivemq.p12'"*

**Impact:** "Cannot find" is misleading — the file exists, it just can't be read. The container restarts repeatedly with the same message, giving no additional diagnostic information. A developer with less Linux experience would not know to check file permissions.

**Recommendation:**
- Improve the error message: distinguish between "file not found" and "file not readable" (`ENOENT` vs `EACCES`). The OS gives you this for free.
- Add a startup health check that validates TLS config before attempting to bind: *"KeyStore found at path X but not readable by current process (uid=10000). Check file permissions."*
- Document the permissions requirement explicitly in the TLS configuration guide with a one-liner: `chmod 644 your-cert.p12`.

---

### 3. `config.xml` read-only warning on every startup is noise
**What happened:** Every startup logs `WARN — The configuration file /opt/hivemq/conf/config.xml is read only and cannot be written by HiveMQ.` This is expected behavior when mounting a read-only config from a Docker volume.

**Impact:** Creates false alarm. A developer seeing a WARN on every boot wonders if something is wrong.

**Recommendation:** Downgrade to INFO or suppress entirely when the config was successfully read. The write attempt is for dynamic config reload — it's not critical for operation. Alternatively, document that this WARN is expected in read-only mount setups.

---

### 4. Security warning drowns out legitimate startup errors
**What happened:** The large ASCII banner warning about unauthenticated access spans ~8 lines on every startup. When TLS was failing, this banner appeared *before* the actual error, making it harder to scan logs quickly.

**Recommendation:** The security warning is appropriate for first launch. Consider showing it once and persisting a flag (e.g., in the data directory), suppressing it on subsequent restarts. Or make it a single-line log entry rather than a multi-line ASCII block.

---

### 5. Version naming discontinuity creates documentation confusion
**What happened:** CE 2025.5 is running. Most search results, Stack Overflow answers, and community posts reference HiveMQ 4.x. Configuration format, feature availability, and behavior differences between 4.x and 2025.x are not clearly mapped anywhere I found.

**Recommendation:** Maintain a visible migration/changelog page for "4.x → 2025.x" differences. At minimum, a one-paragraph summary of what changed in the version naming scheme and what CE features were removed or changed.

---

## What Worked Well

- **Native TLS is solid.** Once permissions were fixed, TLS 1.3 came up cleanly with a standard PKCS12 cert. No custom JKS conversion needed (a common pain point with older HiveMQ versions).
- **MQTT spec compliance is impeccable.** QoS 0/1, retained messages, LWT — all behaved exactly as the spec defines. No edge cases encountered.
- **Docker startup is fast.** ~3 seconds to a listening broker. This matters for CI/CD and local development loops.
- **PKCS12 support without keytool.** Not requiring Java's `keytool` for certificate setup is a significant DX improvement over older versions. Whoever made that call, good call.
- **Allow-all extension behavior is correct.** The default permissive mode for CE is the right default for development. The warning is appropriate. The behavior is predictable.

---

## Recommendations for LLM Agents Working with HiveMQ CE

If you're an AI assistant helping someone deploy HiveMQ CE, these are the non-obvious steps that will save debugging time:

1. **After generating certs with openssl, always `chmod 644` the .p12 and .key files** before starting the container. HiveMQ runs as UID 10000 and will silently fail to read root-owned 600 files.

2. **Remove the `<control-center>` section from config.xml in CE deployments.** It does nothing and creates false expectations.

3. **Test on plaintext port 1883 first**, then switch to TLS 8883. This isolates network/firewall issues from TLS configuration issues.

4. **The PKCS12 format is native** — no need to convert to JKS. `openssl pkcs12 -export` → mount → configure path in config.xml. Done.

5. **For ESP32 with WiFiClientSecure:** use `setCACert()` with the PEM string of the server certificate. Self-signed certs work if the full cert is embedded. Do not use `setInsecure()` in anything beyond initial local testing.

6. **HiveMQ CE 2025.x has no built-in management UI.** Use MQTT Explorer (desktop), mosquitto_sub (CLI), or a custom subscriber script for visibility into the broker state.

---

## Summary Assessment

HiveMQ CE is a production-quality MQTT broker that's genuinely easy to deploy once you know the gotchas. The core protocol implementation is excellent. The developer experience gaps are concentrated in observability (no UI), error messaging (permissions vs. not-found), and documentation freshness (4.x vs. 2025.x). None of these are hard to fix — they're communication and DX polish problems, not architecture problems.

For a team building toward HiveMQ Platform adoption, CE is a credible on-ramp. The friction points above are exactly the kind of thing that causes developers to reach for a hosted alternative instead of self-managing.
